# Classic tutorial guide increment

Behavior baseline: AcademyCraft **1.0.7**, expected commit `00d19ec0cf538f61c1095c9292f5ee6863db4521`, with LambdaLib **1.2.3**. This implementation restores the tutorial item, its fourteen research pages, persistent player state, direct guide entry and source guide presentation. Terminal installation/apps are restored by the independent increment documented in `docs/TERMINAL_APPS_FIDELITY.md`; achievements remain a separate increment. Existing third-party songs, covers and song-item artwork remain excluded.

## Runtime semantics retained

- `academy:tutorial` is a real default-stack-64 item. Recipe48 is shapeless **one vanilla book + one low Imag crystal → one tutorial**. Right-click opens the guide and retains the item. The source localized name remains “MisakaCloud Terminal” even though this item is the tutorial guide.
- Original page order is welcome, ores, phase_generator, solar_generator, wind_generator, metal_former, imag_fusor, terminal, ability_developer, ability_basis, energy_bridge, misc, develop_ability, wireless_network. Welcome, ability_basis, misc, develop_ability and wireless_network are default-visible; they are not gratuitously added to the persistent activated set.
- Conditions are **remembered actual events**, not inventory inspections. Each of21 source targets has independent crafted/picked-up/smelted bits,63 in total. Either event for either listed page target suffices. Removing the acquired stack does not revoke research; an inventory insertion without an event does not acquire it. NeoForge successful pickup uses `ItemEntityPickupEvent.Post.getOriginalStack()` because the picked-up entity may already hold an empty residual stack.
- Visibility evaluates remembered conditions immediately as original `ACTutorial.isActivated` does. Dirty notification/activation batches run every **three local player-data ticks**, in original page order. Each newly activated non-default page posts `TutorialActivatedEvent` on the server and its local client; the batch synchronizes even when a new condition bit belongs to an already activated page.
- Original `generic.giveCloudTerminal` remains default-true as `giveCloudTerminal` in `academy-tutorial-server.toml`. Its misleading name is preserved: after **ten local ticks**, it drops the actual tutorial `ItemEntity` at player `(X,Y+1,Z)`, rather than a terminal installer. Its schedule is latched when the player data is constructed; later config changes do not retroactively create/remove that data part's schedule. The acquired flag changes after the drop attempt; a grant alone has no source sync. Repeat10-tick schedules and reloaded acquired state do not grant again.
- Saved condition bits, activated IDs, acquired flag and Misaka number survive player save/logout/reload/clone. Misaka numbers use the source exclusive range **1000≤ID<19000**. Surplus condition bits and unknown/default activated IDs are preserved just as original NBTS11n did. Source `dirty` and the3/10 tick counters are transient: reloading a pending dirty bit resets the counters and loses that pending activation notification, while the page remains visible from its remembered bit. A later changed condition can trigger the batch.

## Modern adaptations and conditional content

The runtime uses semantic modern item IDs and a stable page-ordered bit ledger. Source annotation registration used an unordered class set; the order of the three dynamically generated non-preinstalled app items is therefore not claimed deterministic across all1.7.10 startups. Tests execute original ModuleTutorial with all app-order permutations and compare semantic condition/preview sets. This is a new modern save format, **not an importer for classic worlds or binary condition indices**.

Missing phase/wind/RF devices are honest conditional references. The terminal installer and three app installers now bind to their actual independent terminal increment. No AIR alias, stand-in item, dummy device, fake obtainable recipe or inventory-based unlock is registered. If a genuine device is later registered, actual crafted/pickup/smelt events for its semantic ID naturally satisfy its existing condition. The independent Metal Former increment is not implemented or copied here.

The server sends an authoritative state snapshot when the actual tutorial item is used, with a narrow held-item-validated `tutorial_open` wire ingress. Common classes do not reference client namespaces. Server state stores the original client entity `AC_Tutorial_Open` first-open flag so the initial guide animation survives a modern restart; an opening packet carries its pre-open value, then the server saves the flag. Dead, removed and spectator requests and malformed/unheld open requests are rejected. This is a modern transport/persistence adaptation to the old client-only right-click.

Original English and Simplified Chinese Markdown is preserved byte-for-byte under lowercase modern resource paths. Other selected languages fall back to English as original `ACTutorial.getContent` did. Inline original key and Misaka substitutions, list/headings/emphasis/image tags, scrolling, learned-before-locked page order, locked brief and preview access, source windows/logos/fonts, first-open transition, preview tag/subview controls and guide-update notification have dedicated client adapters. They query genuine registered items and live crafting/furnace recipes. Additional machine or unsupported-device recipe cards remain explicitly labeled source references. Their presentation does not certify obtainability or machine execution.

Original system-font choice and font rasterization depend on fonts actually installed in the current runtime, just as LambdaLib did. No proprietary or third-party font file is redistributed. Source UI geometry and time curves are tested; they do not establish equal pixels between1.7.10 and1.21.1 renderers.

The guide retains source singleplayer pause behavior while its first-open logos and preview rotations use absolute time. Modern previews use the registered GUI item/block model and modern shader pipeline. They do not reproduce the old `ViewGroups.drawsBlockImpl` write to world block `(0,0,0)` or its legacy GLU projection. Client state refresh can update the learned-before-locked list while the screen is open; original GuiTutorial initially captured that list. Keyboard page navigation is a modern accessibility addition. The original Markdown bytes remain intact; contextual reference notices identify unavailable devices/apps mentioned by default-visible source pages.

## Evidence boundaries

Packaged immutable source witnesses and narrow independent compiler shims execute original ModuleTutorial, Conditions, TutorialData, ACTutorial, TutorialRegistry, ItemTutorial, TickScheduler and RandUtils. They are portable classpath fixtures with pinned hashes and original notices, not reads from `.reference` or a staging directory. Differential checks cover every target/event, app-order permutations, source scheduling/config/notification ordering, clone/reload persistence and seeded multi-event traces. Actual modern NBT/event-bus checks, promoted-source/resource bindings, common cold-link checks with client namespaces denied, and client Markdown/layout/media/timeline checks are separate suites.

The five finite native GameTest fixtures compile against cached official NeoForge21.1.252/Minecraft1.21.1 APIs. They prepare actual guide registry/crafting ResultSlot consumption/right-click, first-login guide entity/grant timing, successful native solar pickup and remembered OR activation, crafted/smelted ingress plus player clone, and held-item protocol rejection/reopening. **They have not been launched by this stage.** The main integration owner must run Gradle/native/client acceptance in its serial lane and inspect direct guide opening, EN/ZH fallback, scrolling/resizing/locked pages/previews/notifications, save/restart retention and source timing before claiming live acceptance.

No native server or client, desktop UI, capture, Gradle, user computer, paid service, publication, push or EULA operation is performed by this isolated stage. A passing headless oracle does not prove a natural survival playthrough, multiplayer, visual/audio equivalence or third-party interoperability.
